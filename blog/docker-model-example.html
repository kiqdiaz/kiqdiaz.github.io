Docker IA LLM

Ejecutando modelos de IA localmente con Docker:
una guía práctica

Luis Cueva Díaz Julio 2026 8 min de lectura

Cualquier desarrollador que ha trabajado en un sistema con datos reales —un Django, un Rails, el stack que sea— conoce la fricción: para responder algo tan simple como "¿cuántos pedidos se cancelaron la semana pasada y por qué?" terminas escribiendo un query a mano o navegando el admin a punta de clics y filtros. Quería resolver eso: poder preguntarle a mi sistema en lenguaje natural y que él mismo genere y ejecute el SQL correcto.

Lo interesante no fue el "qué" sino el "con qué modelo". Empecé con Llama 3.2, que resultó demasiado limitado: apenas el query pedía un join o un group by, alucinaba columnas que no existían. Probé DeepSeek-R1 esperando mejor razonamiento, y lo tuvo — de sobra: al ser un modelo "thinking" se ponía a especular sobre el esquema antes de responder, y cada query simple tardaba varios segundos. El punto intermedio apareció con Qwen: suficientemente capaz para joins y agregaciones, sin la latencia ni el sobre-pensamiento de un modelo de razonamiento. Los tres corriendo enteramente en local, sin pagar por ninguna API, gracias a Docker Model Runner — y de ahí nació docker-model-example, el proyecto de referencia que uso en este artículo.

¿Qué es Docker Model Runner?

Introducido en Docker Desktop 4.40 (mayo 2025), Docker Model Runner añade un subcomando docker model que trata a los modelos de IA igual que a cualquier imagen de contenedor: los descargas de un registro, los ejecutas y los integras con tus servicios existentes via API REST compatible con OpenAI.

El flujo central tiene tres comandos: 

# 1. Descargar el modelo desde Docker Hub
docker model pull ai/qwen2.5:3B-Q4_K_M

# 2. Probarlo en consola interactiva
docker model run ai/qwen2.5:3B-Q4_K_M

# 3. Exponerlo como API local (puerto 12434)
docker model run --detach ai/qwen2.5:3B-Q4_K_M
Dato importante: el endpoint de la API es compatible con el formato de OpenAI, así que cualquier cliente que uses con GPT-4 funciona sin modificaciones apuntando a http://localhost:12434/engines/v1.

El proyecto docker-model-example

La idea del proyecto es demostrar un caso de uso realista: un servicio web que acepta preguntas, las envía al modelo local y devuelve respuestas, todo dentro de una red Docker aislada. La estructura es deliberadamente simple: 

docker-model-example/
├── docker-compose.yml
├── app/
│   ├── Dockerfile
│   ├── main.py        # FastAPI → llama al modelo
│   └── requirements.txt
└── README.md

El docker-compose.yml central

La clave está en cómo se declara el modelo como un servicio especial con el proveedor model: 

services:
  llm:
    provider:
      type: model
      options:
        model: ai/qwen2.5:3B-Q4_K_M

  app:
    build: ./app
    ports:
      - "8000:8000"
    environment:
      - MODEL_ENDPOINT=http://model-runner.docker.internal/engines/v1
    depends_on:
      - llm

Docker se encarga de descargar el modelo, inicializarlo y exponerlo en la red interna de Docker bajo el hostname model-runner.docker.internal. Tu app solo necesita apuntar ahí.

El lado de la aplicación

En main.py uso el cliente oficial de OpenAI apuntando al endpoint local. Sin cambiar una sola línea de lógica de negocio: 

from openai import OpenAI

client = OpenAI(
    base_url="http://model-runner.docker.internal/engines/v1",
    api_key="not-needed",
)

def ask(question: str) -> str:
    response = client.chat.completions.create(
        model="ai/qwen2.5:3B-Q4_K_M",
        messages=[{"role": "user", "content": question}],
    )
    return response.choices[0].message.content

Levantarlo todo con un comando

docker compose up

# Primera ejecución: descarga el modelo (~2 GB)
# Siguiente: arranca en segundos desde caché

El modelo se descarga una sola vez y queda cacheado localmente. Las ejecuciones siguientes son casi instantáneas.

Lo que aprendí construyendo esto

Hay tres cosas que me sorprendieron positivamente:

  • Cero fricción de dependencias. No hay conda, no hay pip install torch de 3 GB, no hay conflictos de CUDA. El modelo corre dentro del runtime de Docker y ya.
  • Aislamiento real. El modelo solo es accesible dentro de la red Docker. No hay nada escuchando en puertos públicos a menos que tú lo decidas explícitamente.
  • Portabilidad inmediata. Cualquier colega con Docker Desktop puede clonar el repo y tener el mismo entorno en minutos. Sin instrucciones de setup de tres páginas.

El punto negativo más notable: la primera descarga del modelo es lenta y pesada (Qwen2.5 3B en Q4_K_M pesa alrededor de 2 GB). En equipos grandes querrás precargar el modelo en la imagen base o usar un registry interno.

¿Cuándo usar esto?

Docker Model Runner tiene sentido cuando necesitas:

  • Desarrollar features de IA sin pagar por APIs externas en cada iteración
  • Mantener datos sensibles dentro de tu red (regulaciones, privacidad)
  • Reproducibilidad: el mismo modelo, la misma versión, en todos los entornos
  • Integrar un LLM como un servicio más dentro de un stack Docker Compose existente

No es el reemplazo para producción con modelos grandes o alta concurrencia — ahí los modelos como servicio (AWS Bedrock, Vertex AI, etc.) siguen siendo la opción correcta. Pero para desarrollo local y pruebas de concepto, este flujo es imbatible en simplicidad.
